---
name: GitHub connection workflow scope and hosted-run verification
description: What the Replit GitHub connection cannot do for .github/workflows files, how to get a real Actions run for a workflow that only exists in the workspace, and how to read job summaries that GitHub hides.
---

The Replit GitHub connection lacks the `workflow` OAuth scope. It can dispatch and cancel runs, read run/job/check-run metadata, list branches, create or delete non-workflow refs, and comment on pull requests, but it cannot read or write `.github/workflows/*` contents (contents reads 403; ref updates whose commits touch a workflow 404; contents PUT to that path is blocked at the proxy). Job log downloads through the connection also fail (403 on the blob redirect).

**Why:** Until 2026-09-15 the workspace and GitHub histories of this repo diverged (GitHub `main` was far behind and lacked the release pipeline), and the repo is public with redactions that the workspace tree did not have, so pushing the whole workspace would have leaked those files. On 2026-09-15 `main` was joined by a real two-parent merge and pushed, so `main` is shared history now; `development` and `production` on GitHub were fast-forwarded to `main` on 2026-09-19 (see `github-branch-sync.md`).

**Push credentials (2026-09-15, re-checked 2026-09-16):** the shell's platform `replit-git-askpass` credential (username `token`) was rejected by GitHub ("Invalid username or token"), so `git push` from the shell and the Git pane's own Push both fail until the owner reconnects GitHub under Replit account settings → Git Providers (that OAuth grant carries `repo` + `workflow`). Check with `git push --dry-run origin main` before planning any push; a public repo makes `ls-remote`/fetch succeed anonymously, which proves nothing. Owner-provided fine-grained tokens live in secrets whose names change (`GITHUB_WORKFLOW_PUSH_TOKEN` returns 401; `GITHUB_WORKFLOW_PULL_TOKEN_FINAL` is valid until 2026-10-15 but on 2026-09-16 had no `contents=write`, so even a dry-run push was 403). Probing rules: the `permissions` block from `/repos/...` describes the *user's* repository rights, not what the token was granted; the only cheap proof of write access is `git push --dry-run` with the token (the receive-pack advertisement itself needs contents write), and a 403 from a write API call carries an `x-accepted-github-permissions` header naming the missing permission (`contents=write,workflows=write` when workflow files are involved). List secrets with `viewEnvVars`, probe `/user` for identity/expiry without printing the value, and note that a newly added secret takes ~30 s to appear in shell environments. Push through a throwaway `GIT_ASKPASS` script that echoes the variable (username `x-access-token`), with `-c credential.helper=`, and delete the script afterwards.

**Repository rename (found 2026-09-16):** the GitHub repository is now `lisagorewitdecker/RealtimeAlgoChatApp`; the old `RealtimeDevAlgoChat` name returns 404 for anonymous, token, and integration requests alike, so a sudden 404 on every GitHub call means "check the name via the GitHub connection's repo list and fix `origin`", not "the repo is gone". Later the same day a fresh fine-grained token in `GITHUB_WORKFLOW_PUSH_TOKEN` (expires 2026-10-16) pushed `main` including workflow files through the throwaway-askpass recipe, while the platform credential behind the Git pane was still rejected — the pane's own push works only after the owner reconnects GitHub under Git Providers.

**Fork remote relationship (2026-09-19):** the workspace's requested `Lisa-Gorewit-Decker/RealtimeDevAlgoChatApp` fork is now `origin`; the former GitHub remote is preserved as `upstream`. The fork currently advertises only `main`, while local `development` and `production` are configured to track their corresponding fork branch names and show as absent until those branches are published. The authorized GitHub connection can read the fork and reports push permission, but the shell Git credential still rejects a no-op `git push --dry-run`; do not push until the owner reconnects the Git provider or supplies an approved transport.

**Public-repo redactions:** before pushing workspace history, `git grep -l REDACTED origin/main` and diff those files against the local tree; GitHub had replaced a Datadog intake key in a pasted attachment with `[REDACTED]` while the workspace copy still had the raw value. Apply the redaction at the tip (`git checkout origin/main -- <file>`); GitHub's own upload commits already contained the raw value, so no history rewrite was needed — rewriting `main` would also break every in-flight task branch's merge base.

**How to apply:**
- To run a workspace-only workflow on GitHub, ask the owner for a fine-grained token (Contents + Workflows write, Actions read) through the secrets flow, build a temporary branch from GitHub `main` plus only the files under test with git plumbing (temp index, no working-tree changes), push it with an inline credential helper that reads the secret, dispatch with `publish=false`, and cancel the run while self-hosted jobs are still queued (no runner ever claims them; the `always()` gate then fails by design). The same token downloads `/actions/jobs/{id}/logs`. Delete the branch afterwards and tell the owner to revoke the token.
- GitHub shows job summaries only to signed-in viewers, and neither REST nor GraphQL check-run `output` carries them, so a signed-out browser or the API cannot confirm the rendered block. To review the hosted bytes, run an extra step on the verification branch that repeats the scenario and echoes its summary through `scripts/run-untrusted-checker.sh` into the log; leave the verified steps unchanged.
- When raw Actions logs return 403, check-run annotations still expose action-level failures (for example, setup-node's rejected version) and can prove the failing step and offending input, but they do not prove the rendered step-summary text.
- Re-check the temp branch head before reusing it: a pushed branch prompts the owner to open a pull request, and suggestion commits accepted there may not even parse. Verify only against the commit you built, and warn against merging the pull request.
- Only the owner can view the rendered summary; link them to `.../actions/runs/<run>#summary-<job>` and record the hosted evidence in a dated `artifacts/chat-app/docs/*-check-YYYYMMDD.md` record, matching the existing device-check records.
